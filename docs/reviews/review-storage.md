# Final review: the "storage" group

Capabilities: storage-format, storage-indexes, storage-durability, storage-snapshots. Items: 9 (BLOCKER: 5, contradiction: 4). Ordered by descending importance.

## 1. Contradiction: a zero page during WAL replay is a start refusal after an ordinary crash
- **Where:** `storage-format` -> "Checks when opening the file" / scenario "File growth did not reach the disk"; "Common page header and types" / "Zero page"; "File growth and out of space" / "Extended area". Against `storage-durability` -> "Consistency check at start" (pages read during WAL replay are checked) and "Inconsistent database is not opened" (ADR 0053 item 2: a page needed for WAL replay with a wrong checksum is a start refusal).
- **Essence:** a page handed out from a fresh growth chunk after the last checkpoint lies inside the file length and on disk consists of zeros (type 0, wrong checksum). The WAL modifies it, while the start check declares it corrupt and forbids the start. The exception "applied as zero pages" is given by `storage-format` only to pages beyond the end of the file. As a result an ordinary SIGKILL after the database grew leads to a start refusal, which violates CUJ14. It can also be implemented differently: accept zero pages. Then two implementations behave differently.
- **Fix:** record in `storage-durability` and `storage-format` that an all-zero page that a WAL entry initializes completely (the first change after it is handed out) is accepted as empty on recovery, both inside the file and beyond its end. A zero page referenced by a tree or list without such an entry is corruption.

## 2. BLOCKER: `next_S` "not less than the largest S" allows a number version to repeat
- **Where:** `storage-format` -> "Number header and number version" / "Header invariant" ("the header's S is not greater than `next_S`"); `storage-durability` -> "Version does not require a number scan..." / "Counter after a crash" ("`next_S` is not below the largest S"); `storage-snapshots` -> "Contents of the backup control file" ("`next_S` is not less than the largest S in the headers"). Against the scenario "Backup version counter" (the issued S is greater than 500) and ADR 0051 items 2, 7 (`next_S` is the next value to be issued).
- **Essence:** since `next_S` is the next value to be issued, the equality `next_S` = max S is allowed by the requirements but yields a repeat: the next operation on a number with S = max S gets the same version, and the change does not change the version (a violation of X-5, `write-operations` "Version is never repeated"). The "not less" requirement and the scenario "greater than 500" contradict each other.
- **Fix:** in all three places write strictly: `next_S` > the largest S (header S < `next_S`; after a crash `next_S` >= max(`next_S` from WAL entries and from `control`), where each value is already greater than the issued S).

## 3. BLOCKER: a write error at a checkpoint is not defined, and "Disk full" depends on the file growth method
- **Where:** `storage-format` -> "File growth and out of space" / "Disk full"; `storage-durability` -> "Checkpoints bound the WAL", `"Read-only" state`, "Leaving the states".
- **Essence:** extending via `File::set_len` creates a sparse tail and on Linux/macOS usually does not return `ENOSPC`. Space runs out later, when pages are written by a checkpoint, when operations are already acknowledged. The spec does not say what happens then. If this is assigned to "read-only", the probe (a write to the WAL) succeeds, the state becomes normal again, checkpoints still fail, and the WAL grows beyond 256 MiB: "Checkpoints bound the WAL" and start <= 30 s are violated. Implementations on `set_len` and on `fallocate`/`F_PREALLOCATE` give different observable behavior in CUJ16. For `fallocate` there is no API in std; `libc` or an analog is needed, which is one more decision about a crate.
- **Fix:** add to `storage-durability` the behavior on a failed checkpoint: "read-only" or "storage error" by `errno`, and exit from "read-only" only after a successful checkpoint, not a single WAL probe. Define whether file growth reserves blocks (with an ADR on the method), or rewrite the scenario "Disk full" so that it allows a refusal at a checkpoint.

## 4. Contradiction: "word search always completes with a result" versus revocation of a short read's snapshot
- **Where:** `storage-indexes` -> "Word search always completes with a result..." / "A heavy query completes with a result" ("without an error"). Against `storage-snapshots` -> "Snapshot retention ceilings" (30 s, the "snapshot revoked" error) and "Cap on retained volume" (short reads are revoked second).
- **Essence:** a word-search page is a short read. At the retention cap `storage-snapshots` revokes it with an error, while `storage-indexes` forbids any completion with an error except the API timeout. Both requirements cannot be met at once.
- **Fix:** in `storage-indexes` name the exceptions directly: snapshot revocation (`snapshot_revoked`) by the retention cap and the lifetime ceiling, alongside the request timeout of area 3.

## 5. Contradiction: where the file signature lies
- **Where:** `storage-format` -> "Data file header" / scenario "File not from this system" ("the first bytes of `data` are not equal to the signature"). Against "Header fields" / "Layout by offsets" (the signature at offset 32, bytes 0...31 are the common page header with `checksum`).
- **Essence:** by the scenario the first bytes of the file are checked, by the layout bytes 32...39. An implementation following the scenario will reject any genuine database. An implementation following the layout will not pass this scenario.
- **Fix:** in the scenario write "bytes 32...39 of `data` are not equal to the signature".

## 6. Contradiction: write errors on the `retain` temporary file
- **Where:** `storage-durability` -> `"Read-only" state` (any write with `ENOSPC`/`EACCES`/... -> "read-only") and `"Storage error" state` (any other write error, including `EIO`). Against `storage-snapshots` -> "Snapshot retains earlier page versions" / "Temporary file error" (`ENOSPC` in `retain` only revokes snapshots, the database state does not change).
- **Essence:** `retain` lies in the database directory, and the list of causes in `storage-durability` does not exclude it. One requirement needs a transition to "read-only", the other does not. For `EIO` in `retain` the behavior is not defined at all: "storage error" or snapshot revocation.
- **Fix:** in `storage-durability` exclude `retain` from the sources of both states: any I/O error on `retain` only revokes snapshots in the order of "Cap on retained volume".

## 7. BLOCKER: start from a backup when files are not writable
- **Where:** `storage-durability` -> `"Read-only" state` / scenarios "Start on non-writable files" and "Crash shutdown and files not writable". Related to `storage-snapshots` -> "Start from a backup is a new generation".
- **Essence:** the spec defines only a clean shutdown (start in "read-only") and a crash one (refusal). A backup (`run_state = backup`) on a read-only medium, for example an archive on a mounted volume, can reasonably be implemented either as a refusal or as a start in "read-only" on the earlier generation. ADR 0053 item 5 chooses refusal, but this was not carried into the requirement.
- **Fix:** in the scenario "Crash shutdown and files not writable" add a start from a backup: the server does not start and reports the cause (per ADR 0053 item 5).

## 8. BLOCKER: dangling reference to the format of `control`/`dwb`/`wal/` and the place where the backup description lives
- **Where:** `storage-format` -> "Database directory contents and data file" ("the format of `control`, `dwb` and `wal/` is set by `storage-durability`"; "there are no other required files"). Against `storage-durability` (no format) and `storage-snapshots` -> "Backup does not exist until complete", `"Backup" marker in the backup itself`.
- **Essence:** the layout of `control`, `dwb`, segments and the WAL entry is set by no capability. Therefore the scenario "`wal/` or `dwb` from another database" cannot be verified (where `db_id` is in a segment that is "filled with zeros"), nor can the reading of an earlier v1 WAL by a new program after a crash (CUJ11, CUJ14). The "backup description" has no defined location (a separate file or `control` fields) and format, while `storage-format` does not allow a separate file. How "backup incomplete" and "not a database" are distinguished depends on this.
- **Fix:** add to `storage-durability` a requirement on the layout (`control`: two slots with a layout label, ADR 0040 item 1 fields and `db_id`; a segment header with `db_id`; WAL entry fields of ADR 0051 item 2) and on label compatibility within v1. In `storage-snapshots` state where the backup description lives (for example, fields of a `control` slot, or a file with a given name), and add it to the directory contents in `storage-format`.

## 9. BLOCKER: commit number is underspecified, the backup reconciliation scenario is not verifiable
- **Where:** `storage-snapshots` -> "Write operations are strictly sequential" ("within the lifetime of the process"), "One snapshot per request" (a snapshot is "after the first N acknowledged operations"), "Backup point is the LSN at command receipt" / "Reconciliation with the operation sequence".
- **Essence:** it is not stated whether acknowledged "unchanged" operations (an identical retry, a rename to the same name) get a commit number. They are acknowledged but write no WAL entry. The number also resets on restart. The commit number in a backup that is printed to the operator, and the reproduction of "the first N operations" in a test, will diverge between two implementations. For a database that survived a restart, N defines nothing.
- **Fix:** define the commit number as a counter of operations that changed data (excluding "unchanged"), continuous across restarts, for example stored in `control` or the WAL. Or write the snapshot LSN into the backup description and reconcile the backup by LSN.
